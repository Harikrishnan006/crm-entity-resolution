# CRM entity resolution with an auditable rule layer

Duplicate account detection for CRM data, where every recommendation names the
rule that produced it and anything unresolved is escalated instead of guessed.

Built around a question that matters more than the matching itself: **how do
you know the automation is right when a wrong answer looks reasonable?**

```bash
pip install -r requirements.txt
python data/generate_sample_data.py
PYTHONPATH=src python src/dedupe.py
PYTHONPATH=src python src/allocate.py
pytest -v
```

All data is synthetic and generated by the script above. No real or client
records are used anywhere in this repository.

## A failure worth describing

The first version of the name normaliser stripped trailing boilerplate before
comparing companies. `Inc`, `LLC`, `Ltd`, `Corp` — and also `Group` and
`Holdings`, which look like the same kind of noise.

They are not. An incorporation form tells you how a company is registered.
`Group` and `Holdings` usually tell you it is a *different company*, very often
the parent of the one you are comparing it to. Stripping them collapsed two
distinct legal entities into one normalised identity, which disabled the rule
that keeps them apart, and a pair that should have been left alone was
escalated for review instead.

**The failure was silent.** No exception, no warning. The output was a
conservative, defensible-looking recommendation — review it, don't merge it —
which is exactly what a careful reviewer would expect a cautious tool to say.
Nothing about the result invited suspicion.

It surfaced only because the expected outcome for every pair had been written
down before the matching logic existed. Eight pairs, eight expectations, seven
agreed and one did not. That one disagreement was the entire signal.

The lesson is in `tests/expectations.py`: the automation is measured against an
independent reading of the data, never the reverse. At twenty records a manual
check catches this. At twenty thousand it does not, which is the argument for
keeping the expectation table as a test rather than a one-off exercise.

## Why rules rather than a similarity score

A single weighted score cannot express *this evidence is disqualifying no
matter how much other evidence agrees*.

Two companies sharing a domain is the clearest case. It is strong evidence of
a relationship and no evidence at all of identity — a parent and its division
share a domain, and so do a company and the subsidiary that should keep its
own contract. A score sees agreement and pushes the pair toward merge. Scored
on raw similarity, the three groups below are nearly indistinguishable:

| | shared domain | same headcount | same external ref | correct answer |
|---|---|---|---|---|
| Caldera Group / Caldera Field Services | yes | no | no | **keep** — parent and division |
| Orrery Systems / Orrery Systems Integration | yes | yes | no | **review** — boundary unclear |
| Vireo Labs / Vireo Laboratories | yes | yes | yes | **merge** |

So the decision is made by ordered rules, and the score is consulted only when
no rule has fired. Distinctness rules run first, so a genuinely separate
company is never escalated or merged on the strength of a shared domain or a
near-identical name.

| Rule | Condition | Action |
|---|---|---|
| R1 | Legal name, domain and external ref all differ | Keep — different entities |
| R2 | Shared domain, different legal names, corroborated by different headcount + different refs + separate open pipeline | Keep — link, don't merge |
| R3 | Domains differ but external ref or legal name matches | Review — which domain is current? |
| R4 | A related record carries an unresolved-conflict note | Review |
| R5 | Shared domain, different legal names, no corroboration | Review |
| R6 | Score ≥ 70, no blocking rule fired | Merge |
| R7 | Score 45–69 | Review |
| R8 | Score < 45 | Keep |

Every row of output carries its rule and a rationale, so a recommendation can
be traced back to the evidence that produced it rather than taken on trust.

## What the sample data contains

Twenty synthetic accounts arranged into the failure modes that make CRM
de-duplication hard. Several look identical to a naive matcher and require
opposite decisions.

| Group | Pattern | Correct call |
|---|---|---|
| G1 | Clean duplicate, one record a thin import | Merge |
| G2 | Parent and division sharing a domain | Keep, link them |
| G3 | Rebrand — one entity, two domains, neither proven current | Review |
| G4 | 0.97 name similarity, every identifier differs | Keep |
| G5 | Identity certain, live deal under a different owner | Review |
| G6 | Shared domain, differing legal names, nothing corroborating | Review |
| G7 | Three records of one entity, no single pair obvious | Merge as one cluster |
| G8 | Same first word, unrelated companies | Never reaches the rules |
| G9 | Singletons with no candidate pair | — |

Blocking reduces 190 possible pairs to 9 worth evaluating. G8 never reaches the
rule layer at all, which is the point: unrelated companies should cost nothing.

### Transitive clustering

Pairwise matching reports three duplicate records as three separate pairs,
which invites three separate merges and a different surviving ID each time.
Union-find collapses them into one group with one primary, chosen as the lowest
account ID — the oldest surviving record. Deliberately not the most recently
active one, because a rebrand makes recency misleading.

## Lead routing

`src/allocate.py` consumes the resolver's output and distributes outreach-ready
leads across reps under stated capacity. Two things make it more than a filter.

**It reads the resolution queue.** A lead on an account whose identity is still
unresolved is held, not contacted, because otherwise two reps work the same
company under two records.

**It publishes both readings of readiness.** Taking the CRM's duplicate flag at
face value gives one number; treating a repeated role at the same account as a
contact-level duplicate gives a smaller one. Both appear on every row, with the
divergence named. An assumption folded silently into a headline number looks
like a fact to everyone downstream. Stated beside the alternative, it is
something a reviewer can accept or reject in seconds.

Capacity is treated as a ceiling rather than a target: a rep carrying a
significant overdue backlog is given nothing, because adding volume there
produces more backlog, not more outreach.

## Known limitations

Stated rather than hidden, because each one changes how far the output can be
trusted.

- **R4 keyword-matches free-text notes written by humans.** A note reading
  "ownership differs" rather than "owner conflict" will not fire. This is the
  weakest link and the first thing to replace with a structured conflict flag.
- **Some pairs are separable only by those notes.** Groups G1 and G5 are
  identical on every structured field. If the note were absent the resolver
  would merge both, which is precisely why merges stay recommendations rather
  than actions.
- **Name similarity is character-level** (`difflib`). It will not connect an
  acronym to its expansion — "IBM" and "International Business Machines".
- **The thresholds are judgement calls** tuned on twenty records. They need
  re-tuning against a labelled sample, reported as precision and recall, before
  anyone runs this at real volume.
- **Nothing writes back to a CRM.** Output is a recommendation file. A
  production version needs a staging table, a dry-run mode and a reversible
  audit trail before it is allowed near live records.

## Layout

```
src/normalise.py   normalisation and similarity; the suffix lesson lives here
src/rules.py       the ordered rule layer, scoring, transitive clustering
src/dedupe.py      resolver CLI
src/allocate.py    capacity-aware lead routing
data/              synthetic dataset generator and its CSV output
tests/             expectations table and the suite that asserts against it
```

No LLM call sits anywhere in the decision path. Merge recommendations have to
be deterministic, reproducible and inspectable — the same input must produce
the same output every time, and the reason has to be readable. A model call is
none of those things.
