# CRM Entity Resolution

Finds duplicate company records in CRM data, and knows when **not** to merge them.

Every recommendation names the rule that produced it. Anything uncertain gets escalated to a human instead of guessed at.

![verify](https://github.com/Harikrishnan006/crm-entity-resolution/actions/workflows/verify.yml/badge.svg)

---

## The problem

Two account records look similar. Should you merge them?

It sounds like a string-matching problem. It isn't. Here are three pairs from the sample data:

| Pair | Shared domain | Same headcount | Same external ref | Correct answer |
|---|---|---|---|---|
| Caldera Group / Caldera Field Services | yes | no | no | **Keep** — parent and division |
| Orrery Systems / Orrery Systems Integration | yes | yes | no | **Review** — boundary unclear |
| Vireo Labs / Vireo Laboratories | yes | yes | yes | **Merge** |

All three share a domain. All three have near-identical names. They need three different answers.

Merge the first and you collapse two live contracts into one account. Skip the third and your reporting stays wrong. A similarity score can't tell them apart, because a shared domain is strong evidence of a *relationship* and no evidence at all of *identity*.

## How it decides

Rules run in order. The first one that matches wins. The similarity score is only consulted when **no** rule has fired.

| Rule | Condition | Action |
|---|---|---|
| R1 | Legal name, domain and external ref all differ | **Keep** — different companies |
| R2 | Shared domain, different legal names, backed by different headcount + different refs + separate open deals | **Keep** — link, don't merge |
| R3 | Domains differ but external ref or legal name matches | **Review** — which domain is current? |
| R4 | A related record carries an unresolved-conflict note | **Review** |
| R5 | Shared domain, different legal names, nothing corroborating | **Review** |
| R6 | Score ≥ 70, no blocking rule fired | **Merge** |
| R7 | Score 45–69 | **Review** |
| R8 | Score < 45 | **Keep** |

**Distinctness rules run first.** That's the key design choice. A genuinely separate company is never merged or escalated just because it shares a domain or has a similar name.

Signals and weights: external reference (40), domain (25), legal name (25), name similarity (8–15), city and headcount (5 each). External ref is heaviest because two rows sharing one trace back to the same source record.

## A bug worth describing

The first version of the name normaliser stripped trailing boilerplate before comparing: `Inc`, `LLC`, `Ltd`, `Corp` — and also `Group` and `Holdings`, which look like the same kind of noise.

They aren't. An incorporation form tells you how a company is *registered*. `Group` and `Holdings` usually tell you it's a **different company** — often the parent of the one you're comparing it to.

Stripping them collapsed two separate legal entities into one identity. That disabled the rule meant to keep them apart, and a pair that should have been left alone got escalated instead.

**The failure was silent.** No exception. No warning. The output was a cautious, sensible-looking "review this one" — exactly what you'd expect a careful tool to say. Nothing about it invited suspicion.

It surfaced only because the expected answer for every pair had been written down *before* the matching logic existed. Eight pairs, eight expectations. Seven agreed. One didn't. That single disagreement was the entire signal.

That table lives in `tests/expectations.py`, and `test_entity_words_are_not_stripped` is the regression test. The automation is measured against an independent reading of the data — never the other way round.

At 20 records a manual check catches this. At 20,000 it doesn't.

## The sample data

20 synthetic accounts, arranged into the patterns that make this hard:

| Group | Pattern | Correct call |
|---|---|---|
| G1 | Clean duplicate, one record a thin import | Merge |
| G2 | Parent and division sharing a domain | Keep, link them |
| G3 | Rebrand — one company, two domains, neither proven current | Review |
| G4 | 0.97 name similarity, every identifier differs | Keep |
| G5 | Identity certain, live deal under a different owner | Review |
| G6 | Shared domain, different legal names, nothing corroborating | Review |
| G7 | Three records of one company, no single pair obvious | Merge as one cluster |
| G8 | Same first word, unrelated companies | Never reaches the rules |
| G9 | Singletons with no candidate pair | — |

Blocking cuts 190 possible pairs down to 9 worth evaluating. G8 never reaches the rule layer at all — unrelated companies should cost nothing.

**Transitive clustering:** three duplicate records show up as three separate pairs, which invites three separate merges and a different surviving ID each time. Union-find collapses them into one group with one primary — the lowest account ID, i.e. the oldest record. Deliberately not the most recently active one, because a rebrand makes recency misleading.

## Lead routing

`src/allocate.py` takes the resolver's output and distributes outreach-ready leads across reps under stated capacity.

Two things make it more than a filter:

**It reads the resolution queue.** A lead on an account whose identity is still unresolved gets held, not contacted — otherwise two reps work the same company under two records.

**It publishes both readings of "ready".** Take the CRM's duplicate flag at face value and you get one number. Treat a repeated job title at the same account as a likely duplicate person and you get a smaller one. Both appear on every row, with the difference named.

An assumption folded silently into a headline number looks like a fact to everyone downstream. Stated next to the alternative, it's something a reviewer can accept or reject in seconds.

Capacity is a ceiling, not a target: a rep carrying a big overdue backlog gets nothing, because adding volume there produces more backlog, not more outreach.

## Known limitations

Stated rather than hidden, because each one changes how far you can trust the output.

- **R4 keyword-matches free text written by humans.** A note saying "ownership differs" instead of "owner conflict" won't fire. Weakest link, and the first thing to replace with a structured flag.
- **Some pairs are separable only by those notes.** Groups G1 and G5 are identical on every structured field. Without the note the resolver would merge both — which is exactly why merges stay recommendations, not actions.
- **Name similarity is character-level** (`difflib`). It won't connect "IBM" to "International Business Machines".
- **The thresholds are judgement calls** tuned on 20 records. They need re-tuning against a labelled sample, reported as precision and recall, before running at real volume.
- **Nothing writes back to a CRM.** Output is a recommendation file. Production needs a staging table, a dry-run mode and a reversible audit trail first.

## Layout

```
src/normalise.py   normalisation and similarity; the suffix lesson lives here
src/rules.py       the ordered rule layer, scoring, transitive clustering
src/dedupe.py      resolver CLI
src/allocate.py    capacity-aware lead routing
data/              synthetic dataset generator and its CSV output
tests/             expectations table and the suite that asserts against it
```

No LLM sits anywhere in the decision path. Merge recommendations have to be deterministic, reproducible and inspectable — same input, same output, every time, with a readable reason. A model call is none of those things.
